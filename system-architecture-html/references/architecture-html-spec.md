
# 系统架构设计 HTML 编写规范

## 目录

1. 目标与项目输入
2. 信息处理规则
3. 输出文件与页面结构
4. 整体架构图、流程图、时序图与 ER 图
5. API、技术选型、部署运维、业务名词与节点详情
6. 统一数据、页面交互、响应式与无障碍
7. 一致性、待确认事项、验收与交付报告
 
## 一、目标
 
根据调用者提供的需求文档、现有代码、参考资料和补充说明，产出结构完整、内容一致、可交互、可下钻、可追溯的系统架构设计 HTML。
 
本提示词只规定设计文档的组织、表达、交互和验收规范，不预设具体业务模块、架构分层、技术组件、流程场景或数据库表。
 
所有具体设计内容必须从本次输入资料中提取、分析或推导。
 
# 二、本次项目输入
 
由调用者在使用时填写：
 
- 系统名称：`{系统名称}`
- 需求文档目录：`{需求文档目录}`
- 现有代码目录：`{现有代码目录，可选}`
- 参考架构图：`{参考架构图路径，可选}`
- 输出目录：`{输出目录}`
- 技术栈约束：`{技术栈约束，可选}`
- 补充设计要求：`{补充要求，可选}`
 
# 三、信息处理规则
 
## 1. 信息来源优先级
 
发生冲突时，按以下顺序处理：
 
1. 调用者明确说明
2. 已确认的需求和设计文档
3. 现有代码和已经使用的公共组件
4. 参考架构图
5. 通用架构设计原则
6. 本次架构推断
 
## 2. 设计结论分类
 
重要设计结论必须标明为以下一种：
 
- 已有事实
- 本次设计决策
- 架构建议
- 待确认事项
- POC 验证项
 
不得把未经确认的设计推断写成既定事实。
 
## 3. 内容提取原则
 
必须先分析输入资料，再确定：
 
- 系统边界
- 使用者和外部系统
- 架构分层
- 模块划分
- 功能列表
- 业务流程
- 业务场景
- 接口列表
- 领域对象
- 数据库表
- 业务名词
- 技术选型与版本
- 部署模式与运行拓扑
- 运维责任、可观测性、SLO 和灾备要求
- 非功能要求
- 风险和待确认事项
 
不得预先套用固定业务模块或固定流程。
 
# 四、输出文件规范
 
所有文件放入调用者指定的输出目录。
 
至少包含：
 
- `index.html`：系统架构设计主页面
- `api.html`：使用本地 Swagger UI 渲染的 API 接口页面
- `openapi.json`：OpenAPI 3.1.0 HTTP API 契约唯一事实源
- `styles.css`：统一样式
- `app.js`：页面交互与图形渲染
- `architecture-data.js`：架构设计统一数据源
- `openapi-runtime.js`：Swagger UI 初始化、降级与稳定 Operation ID 定位
 
要求：
 
1. `index.html` 是系统设计总入口。
2. 主页面包含架构图、流程图、时序图、数据库 ER、API 入口和业务名词。
3. `api.html` 可以通过本地静态服务器独立访问，并加载 `openapi.json`。
4. 主页面需要内嵌或集成 API 页面。
5. 主页面节点可以超链接定位到 `api.html` 内的具体接口。
6. 主页面和 API 页面必须共用同一个 `openapi.json`；`architecture-data.js` 只保存 `operationId` 引用，禁止维护两套接口定义。
7. 页面使用静态 HTML、CSS 和 JavaScript 实现；流程图与时序图使用 Mermaid 渲染，整体架构图使用 Cytoscape.js 渲染，ER 图可使用 SVG 或 Mermaid。
8. 不依赖编译和构建步骤。
9. 不依赖外部 CDN；Mermaid、Cytoscape.js、Swagger UI 和运行时从技能 `assets/` 复制到输出目录。
10. 通过本地静态服务器启动后应能完整运行。
11. 至少同时包含 `diagram-theme.css`、`diagram-runtime.js`、`openapi-runtime.js`、`vendor/mermaid.min.js`、`vendor/cytoscape.min.js`、Swagger UI 的 CSS/JS/Source Map 和第三方许可证文件。

`index.html` 至少包含以下主要区域：
 
1. 系统设计总览
2. 整体分层与模块架构
3. 技术选型与部署运维
4. 功能流程图
5. 业务场景时序图

8. 业务名词

10. 风险与待确认事项
 
每个主要区域必须：

- 可以通过 URL Hash 定位
- 通过 Hash 定位时自动展开
- 在主导航中具有对应入口

- 其他区域默认折叠
- 提供“全部展开”和“全部折叠”操作
 
# 六、整体架构图规范

整体架构图必须使用 Cytoscape.js compound graph 实现。层映射为复合父节点，模块映射为所属层的子节点，模块关系映射为 Cytoscape edge。不得继续使用普通 HTML 卡片配合绝对定位线条作为新建架构图的默认实现。

创建、修改或验收整体架构图前，完整读取 `diagram-rendering.md`。
 
## 1. 分层
 
根据输入资料和系统职责确定合理分层。
 
每层必须明确：
 
- 层名称
- 英文名称
- 层级编号
- 核心职责
- 边界说明
- 包含模块
- 允许依赖方向
- 禁止依赖方向
 
不得为了套用模板而创建没有实际职责的分层。
 
## 2. 模块
 
按照高内聚、低耦合原则划分模块。
 
每个模块至少包含：
 
- 唯一 ID
- 模块名称
- 简述
- 所属层
- 核心职责
- 非职责
- 子功能
- 输入
- 输出
- 上游依赖
- 下游依赖
- 关联接口
- 关联数据表
- 关联流程
- 关联时序图
- 代码结构建议
- 设计模式
- 第三方组件
- 扩展点
- 故障边界
- 风险和待确认事项
 
## 3. 架构边界框
 
- 分层使用虚线框表示。
- 模块使用独立节点或虚线边界框表示。
- 层与模块必须有明显的视觉层级差异。
- 模块不能超出所属层的视觉边界。
- 节点文字不能被关系边遮挡。
- 支持画布缩放、拖动、适应视口和恢复视图。
- Cytoscape Canvas 之外提供使用同一稳定 ID 的可访问节点/边列表，保证键盘下钻。
 
## 4. 关系边
 
模块调用关系使用带方向箭头的实线。
 
层级、管理或逻辑归属关系使用带方向箭头的虚线。
 
每条边至少包含：
 
- 唯一 ID
- 源节点
- 目标节点
- 关系名称
- 关系类型
- 调用方向
- 交互目的
- 协议或机制
- 同步或异步
- 输入
- 输出
- 失败处理
- 关联流程
- 关联时序
 
## 5. 关系边视觉要求
 
普通状态下，关系边只能作为辅助信息：
 
- 模块实线建议为 `0.8px–1px`
- 层级虚线建议为 `0.6px–0.8px`
- 普通透明度建议为 `25%–40%`
- 箭头和标签同步降低视觉权重
- 多条线交叉时，尽量减少文字遮挡
- 不得使用过粗或高饱和线条压过节点内容
 
悬浮或键盘聚焦时：
 
- 只增强当前关系边
- 提高当前边的线宽和透明度
- 突出对应箭头和关系热点
- 其他边保持原状态
- 移出后恢复普通样式
 
# 七、功能流程图规范

功能流程图区域使用 Tab 组织。

每个 Tab 对应一个独立流程图。

每个流程图必须由 `architecture-data.js` 生成 Mermaid `flowchart` DSL，再通过本地 Mermaid 显式渲染为 SVG。禁止将原生 HTML 节点和手工 SVG 连线作为新建流程图实现，禁止维护独立于统一数据的硬编码 Mermaid 业务文本。
 
具体流程必须从输入资料中提取，不预设固定流程名称。
 
流程图按照标准有向流程表达：
 
- 开始节点
- 结束节点
- 处理节点
- 判断节点
- 人工节点
- 外部系统节点
- 数据节点
- 条件分支
- 异常分支
- 重试或补偿路径
 
每条流程至少说明：
 
- 流程名称
- 流程目的
- 触发条件
- 前置条件
- 参与角色
- 参与模块
- 主流程
- 分支流程
- 异常流程
- 终止条件
- 输入
- 输出
- 关联接口
- 关联表
- 关联时序图
 
如果输入资料不足以形成完整流程，应列为待确认事项，不得凭空补全业务规则。

每个流程节点和流程边都必须保留稳定业务 ID。Mermaid 渲染后，将节点、边线和边标签重新绑定到统一数据中的 ID；点击、Enter 或 Space 均打开原有详情逻辑。

每个流程图必须使用统一 Mermaid Viewer，提供适应画布、放大、缩小、100% 重置和全屏按钮；支持拖拽背景平移、双击背景放大、`Ctrl/⌘ + 滚轮` 或触控板捏合缩放。缩放和平移不得破坏节点、边的点击与键盘下钻。
 
# 八、业务场景时序图规范

业务场景时序图区域使用 Tab 组织。

每个 Tab 对应一个独立业务场景。

每个时序图必须由 `architecture-data.js` 生成 Mermaid `sequenceDiagram` DSL，再通过本地 Mermaid 显式渲染为 SVG。禁止将原生 HTML 泳道和手工定位消息线作为新建时序图实现。
 
具体场景必须从输入资料中识别，不预设固定场景。
 
时序图按照 UML 时序语义表达：
 
- 参与者
- 外部系统
- 内部模块
- 数据存储
- 同步调用
- 异步消息
- 返回结果
- 回调
- 条件分支
- 循环
- 超时
- 重试
- 异常
- 恢复或补偿
 
每条时序消息必须有：
 
- 消息名称
- 源参与者
- 目标参与者
- 调用类型
- 输入内容
- 返回内容
- 失败处理
- 关联接口

每个参与者和时序消息都必须有稳定业务 ID。Mermaid 渲染后，将参与者、消息线和消息文字重新绑定到统一数据中的 ID；点击、Enter 或 Space 均打开原有详情逻辑。

每个时序图必须使用与流程图相同的 Mermaid Viewer，支持独立缩放、平移、适应画布、100% 重置和全屏查看。切换时序 Tab、折叠再展开或退出全屏后，图形尺寸和当前交互必须保持有效。
 
# 九、数据库 ER 图规范
 
数据库 ER 图必须根据输入资料、领域对象和接口数据需求生成。
 
不得为了让图完整而虚构没有依据的数据表。
 
数据库表按领域或模块分组。
 
每张表至少展示：
 
- 表名
- 中文说明
- 所属领域
- 所属模块
- 主键
- 外键
- 核心字段
- 状态字段
- 版本或并发字段
- 创建时间
- 更新时间
- 关键索引
- 唯一约束
- 数据生命周期
- 关联接口
 
表关系至少表达：
 
- 1:1
- 1:N
- N:M
- 强依赖或弱引用
- 外键方向
- 级联策略
 
点击表节点可以查看完整字段、索引、约束、关系和归属模块。
 
# 十、API 接口目录规范

创建、修改或验收 API 前完整读取 `openapi-api-rendering.md`。

HTTP API 必须生成合法的 `openapi.json`，默认使用 OpenAPI 3.1.0。`api.html` 使用技能自带的本地 Swagger UI 渲染该文件，不手写第二套接口卡片或树形正文。

每个具备设计依据的 HTTP 接口建模为 OpenAPI Operation：

- 使用唯一、稳定、带 `api-` 前缀的 `operationId`。
- 使用标准 `method + path`、`parameters`、`requestBody`、`responses`、`security` 和 `components.schemas` 表达协议契约。
- 使用 `tags` 组织 Swagger UI 分组。
- 使用 `x-architecture` 保存所属层、模块、功能、来源、表、流程、时序、幂等、并发、超时和重试等架构追溯信息。
- 其他页面使用 `api.html#<operationId>` 直接定位并展开具体接口。
- Swagger UI 启用关键词搜索、Operation ID 展示、折叠和标准 Schema 浏览。
- 静态架构交付默认禁用真实请求提交；不得误调用未知或生产环境。
- “全部接口”仅指输入资料和本次设计实际涉及的接口，不得虚构没有设计依据的 Path、Schema 或示例。
- 已识别但缺少 Method、Path 或请求响应依据的接口进入 `x-pending-interfaces`，说明缺失信息、影响和来源，不得伪造为 Operation。
- OpenAPI 只原生描述 HTTP API；异步消息使用 AsyncAPI，或在交付被限定为单一文件时使用明确标注的 `x-async-interfaces` 最小追溯扩展。
 
# 十一、技术选型与部署运维规范

主页面必须包含稳定 ID `technology-operations`。创建、修改或验收本区域前完整读取 `technology-operations.md`。

本区域至少说明：

- 技术选型：语言与版本、前后端框架、架构风格、设计模式、核心中间件、数据存储、集成协议、安全和测试工具。
- 部署设计：部署模式、环境分层、运行拓扑、网络与数据边界、配置密钥、发布策略、弹性容量和故障恢复。
- 运维设计：责任模式、可观测性、SLI/SLO/SLA、告警、事件响应、变更、备份灾备、容量成本、安全运维和 Runbook。

每项必须记录用途、选择理由、适用范围、备选方案、状态和来源。未确认版本、SLO、RTO、RPO、保留期和责任人必须明确进入待确认事项。

使用统一数据生成简洁的响应式表格；HTML 不复制具体选型正文。逻辑模块架构图与物理部署拓扑分开表达，避免在同一图中混入业务模块、Pod、节点和云资源。

# 十二、业务名词规范
 
业务名词根据输入资料提取，并按领域分组。默认使用 Table 列表展示，不使用业务名词卡片瀑布流。

表格使用 `.design-table-wrap` 和 `.design-table.glossary-table`，建议列为：领域、中文名、英文名、定义、使用范围、关联对象、状态。表头低饱和且可粘性定位；行支持悬浮、焦点、点击、Enter 和 Space 下钻。搜索与领域筛选位于表格上方，窄屏横向滚动只发生在表格容器内。
 
每个业务名词至少包含：
 
- 中文名
- 英文名
- 定义
- 使用范围
- 与相似概念的区别
- 对应领域对象
- 关联模块
- 关联接口
- 关联数据表
- 示例
 
所有架构节点、接口、流程、时序和数据库表应使用统一业务语言。

# 十五、页面交互规范
 
## 1. 折叠与导航
 
- 每个主要区域可以折叠和展开。
- 支持全部展开和全部折叠。
- 主导航保持可见。
- 主导航标识当前浏览区域。
- URL Hash 可以定位区域或具体节点。
- 定位具体节点时自动展开所属区域。
 
## 2. 节点和关系边下钻
 
- 点击节点打开节点详情。
- 点击关系边打开交互详情。
- 详情使用抽屉或模态页面。
- 打开详情时不跳失主设计上下文。
- 关闭详情后焦点返回原组件。
- Mermaid 流程边与时序消息必须在 SVG 渲染完成后绑定事件，不依赖 Mermaid 自动生成的 DOM ID。
- Cytoscape.js 节点与边必须把统一数据 ID 作为元素 ID，并调用与迁移前相同的详情处理函数。
 
## 3. Tooltip
 
鼠标悬浮或键盘聚焦节点、流程节点、表节点、时序消息和关系边时：
 
- 显示 Tooltip
- Tooltip 展示组件类型
- Tooltip 展示组件名称
- Tooltip 展示详细描述
- 关系边展示源组件、目标组件和交互机制
- Tooltip 背景透明度建议为 `55%–65%`
- Tooltip 文字保持清晰
- Tooltip 可以使用轻微背景模糊
- Tooltip 不拦截鼠标事件
- Tooltip 自动避让浏览器边缘
- 移出、失焦、滚动或点击后自动关闭
 
## 4. 组件高亮
 
节点悬浮或聚焦时：
 
- 增强当前节点边框
- 改变当前节点背景
- 增加轻量阴影
- 提高当前节点层级
- 不改变节点尺寸和布局
 
关系边悬浮或聚焦时：
 
- 增强当前关系边
- 增强当前箭头
- 增强当前关系热点
- 其他边保持低视觉权重
 
移动到其他组件时，自动清除前一个组件高亮。
 
## 5. 搜索与筛选
 
至少支持：
 
- 架构节点搜索
- API 搜索
- Swagger UI 的 API 关键词搜索与 Method 展示
- 数据表搜索
- 业务名词搜索
 
搜索结果应高亮，非匹配项可以降低透明度。

## 6. Mermaid 视图控制

- 流程图和时序图的控制栏必须由统一运行时生成，不在各 Tab 手写重复事件逻辑。
- 控制栏至少包含“适应”“缩小”“放大”“100%”“全屏”，按钮具有可访问名称和可见焦点。
- 拖拽只能从图形空白背景开始，不能吞掉节点、流程边、参与者或时序消息的点击事件。
- 支持双击空白背景放大；支持 `Ctrl/⌘ + 滚轮` 或触控板捏合以指针位置为中心缩放。
- 默认缩放范围建议为 `25%–400%`；达到边界时禁用对应按钮。
- 图形视口获得焦点时支持 `+`/`-` 缩放、`0` 适应、`1` 恢复 100%、`F` 全屏、方向键平移。
- 使用 Fullscreen API；浏览器拒绝或不支持时提供固定定位的全屏降级。Escape 必须退出全屏，并恢复页面滚动和合理焦点。
- 每个 Tab 保有独立视图控制器。重新渲染前销毁旧的 ResizeObserver、Fullscreen 和文档级事件监听器。
- Tab 激活、折叠展开、窗口尺寸变化及进入/退出全屏后，仅在“适应”模式下重新计算适配比例；手动缩放状态不得被普通 ResizeObserver 意外重置。
- 全屏和窄屏下工具栏不能遮挡图形；图形只能在 Viewer 内平移，不得引起页面整体横向溢出。
 
# 十六、响应式与无障碍规范
 
## 1. 响应式
 
- 支持常见桌面端尺寸。
- 支持平板和手机尺寸。
- 图表超宽时只在图表容器内部横向滚动。
- 页面整体不得产生横向滚动。
- 抽屉宽度不能超出视口。
- Tooltip 不能超出视口。
- 窄屏下导航可以横向滚动或折叠。
 
## 2. 键盘操作
 
支持：
 
- Tab：切换交互组件
- Enter：打开详情
- Space：打开详情或切换组件
- Escape：关闭 Tooltip 或详情
- `+` / `-`：在 Mermaid 视口聚焦时放大或缩小
- `0` / `1`：适应画布或恢复 100%
- `F`：进入或退出 Mermaid 全屏
- 方向键：在 Mermaid 视口聚焦时平移图形
 
## 3. 可访问性
 
- 所有按钮具有可访问名称。
- 图表具有标题和说明。
- Tooltip 使用 `role="tooltip"`。
- 抽屉或模态页面具有正确语义。
- 当前选中 Tab 使用对应 ARIA 状态。
- 当前折叠状态使用对应 ARIA 状态。
- 颜色不能作为唯一的信息表达方式。
- 焦点状态必须可见。
 
# 十七、设计一致性要求
 
必须保证：
 
- 架构图中的模块名称与详情一致
- 模块详情中的 `operationId` 能够在 `openapi.json` 与 Swagger UI 页面找到
- 模块详情中的表能够在 ER 图找到
- 流程节点可以定位到执行模块
- 时序消息可以通过 `operationId` 定位到接口
- OpenAPI Operation 的 `x-architecture` 可以定位到模块和数据表
- 数据表可以定位到所属模块
- 业务名词可以定位到相关设计元素
- 技术选型、部署项和运维项可以定位到适用模块、风险和来源
 
不得出现孤立、无法追溯的节点、接口或表。
 
# 十八、待确认事项规范
 
信息不足时：
 
1. 不得自行虚构业务规则。
2. 不得生成虚假接口或数据表。
3. 必须记录为待确认事项。
4. 说明缺少什么信息。
5. 说明该信息影响哪些设计。
6. 可以给出建议方案，但必须明确标记为建议。
7. 可以给出多个候选方案和取舍。
